# PR #284 — Cryptographic ticket handoff integration fixture

This **disposable PostgreSQL-only** suite aligns the operator ticket issued in PR #283 (64 lowercase hex characters, 32 random bytes) with a test database protocol. It uses an isolated issuer LOGIN and separate consumer LOGIN, both NOINHERIT/NOBYPASSRLS/no elevated privileges; the issuer can only call a SECURITY DEFINER issuance function and the consumer can only call the separate consumption function. Neither can read ticket records or issue/consume through the other's function.

The database stores only SHA-256 of the *decoded 32-byte token* using installed pgcrypto (not token plaintext), checks the 64-hex syntax, derives expiry from database clock with a bounded 1–30-second TTL, locks a ticket and the synthetic role row, rejects already-used, expired, mismatched or revoked tickets, then consumes atomically. Tests use synthetic identities and synthetic privileges on a fixed disposable loopback database, with random tokens; no production migrations, credentials or grants.

**Unresolved before staging implementation:** PostgreSQL-compatible external ticket issuer bound to a genuine Supabase-authenticated administrator and the **real** Store attempt; issuer account compromise could mint tickets for any operator in this synthetic fixture. A digest is not protection against stealing the original bearer token. Database role and attempt checks must use actual production Store schema, audit, locked rows and short retention. Production atomic correlation and proof gate stay disconnected/denied. No activation of Razorpay POST, capture or Printful.
