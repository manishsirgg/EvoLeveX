# PR #318 — Server-only staging PG credential and TLS bootstrap boundary

This change hardens the **uninstantiated** Node `pg` staging authorization adapter. It now rejects configuration unless the database username is precisely the proposed least-privilege login `evo_store_role_reader_login`; a generic admin, postgres or service account cannot be supplied. It requires a DNS-shaped host other than `localhost`, an in-range port, a nonempty database and password and PEM-shaped certificate material. Existing `ssl:{rejectUnauthorized:true,ca:config.ca}` and 3-second connect/query/statement timeouts are retained, as are `server-only`, per-call client lifecycle and the SQL allowlist.

**Important limits:** these source-level configuration checks do **not** establish valid X.509 parsing, trusted CA chain or SAN/hostname verification in a live TLS handshake; a fake but PEM-shaped string passes the initial shape check and should fail only on actual TLS use. The nominal role is proposed, not provisioned. Credentials and CA continue to be injected from a future audited server bootstrap. This PR must not connect to Supabase or introduce secrets, env variables, a live API route, production migration, privileges or payment/fulfillment activation. Future review must validate certificate rotation, actual CA trust/hostname mismatch rejection, network allowlisting, secret storage/rotation, role capability inventory, monitoring and graceful rollback before any live staging activation.
